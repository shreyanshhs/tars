# TARS 🛰️ Agentic Management & Security

> An agentic AI campus scheduler that re-plans timetables when faculty are absent, nudges students, and escalates to the HOD. Built for **Martian 1.0** (24-hour Agentic AI Hackathon, 25–26 Nov 2026).

---

## The problem
When a faculty member is absent or a room becomes unavailable, colleges usually just cancel the class. Students find out late, sections with low attendance lose even more classes, and nobody keeps a record of who decided what.

## What TARS does
1. **Perceive.** A faculty member reports an absence or disruption from the portal.
2. **Reason.** A Gemini-powered agent checks the timetable, free rooms, faculty workload and attendance. Sections below **75% attendance** are prioritised and their classes are never cancelled first.
3. **Act.** It finds a substitute or a new slot. A hard clash validator (plain code, not AI) blocks double-bookings before anything is saved.
4. **Notify.** The substitute gets a Telegram message with Accept / Decline buttons, and the new slot is added to Google Calendar.
5. **Escalate.** If no one replies in time, TARS escalates to the HOD automatically.
6. **Explain.** Every decision is written to an audit log with the agent's reasoning.

Students see their updated grid live, plus nudges (free slots, deadlines) and an events hub that flags clashes with their classes.

## Architecture

![TARS architecture](docs/architecture.svg)

| Layer | What it does |
|---|---|
| 1. User & Trigger | Faculty Portal, Student Live View, HOD Dashboard |
| 2. Security & Guardrails | Role-based access (only Faculty/HOD can change data), hard clash validator |
| 3. TARS Agentic Brain | Gemini function-calling loop: Perceive → Reason & Tool-call → Act & Log |
| 4A. State & Memory | SQLite (timetable, rooms, faculty workload, attendance), decision audit log |
| 4B. Action & Escalation | Telegram Bot API, Google Calendar API, timeout state machine → HOD |

## Tech stack
- **Frontend:** React · Vite · TypeScript · Tailwind CSS (designed in Google Stitch)
- **Backend:** Python · FastAPI · SQLite · Server-Sent Events
- **AI:** Google Gemini API (function calling)
- **Integrations:** Telegram Bot API (polling) · Google Calendar API (service account)
- **Scheduling:** APScheduler (escalation timers)
- **Built with:** Google Stitch (UI design) · Antigravity (frontend) · Claude Code (backend)

## Getting started

### Prerequisites
- Git
- Python 3.10+ (backend)
- Node.js 18+ LTS (frontend)

### 1. Clone
```bash
git clone https://github.com/YOUR-USERNAME/tars-martian.git
cd tars-martian
```

### 2. Backend (macOS)
```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python3 app/seed.py
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```
API docs: http://localhost:8000/docs

<details>
<summary>Backend on Windows (PowerShell)</summary>

```powershell
cd backend
py -m venv .venv
.venv\Scripts\Activate.ps1   # if blocked: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
pip install -r requirements.txt
py app\seed.py
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```
</details>

### 3. Frontend (any OS)
```bash
cd frontend
npm install
npm run dev
```
Open http://localhost:5173. Set `VITE_USE_MOCK=true` in `frontend/.env` to run without the backend.

If 5173 is busy, Vite picks the next free port (e.g. http://localhost:5176). That's fine: the backend allows
CORS from **any port** on `http://localhost` and `http://127.0.0.1`. Any other origin (a LAN IP, a deployed URL)
must be added to `CORS_ORIGINS` in `.env` (comma-separated exact origins; `*` is never allowed), then restart the backend.

### 4. Environment variables
The `.env` file goes in the **repo root**, next to `.env.example` (not in `backend/` or `frontend/`):
```
tars/
├── .env.example
├── .env          ← you create this
├── backend/
└── frontend/
```
macOS / Linux: `cp .env.example .env`

**Windows (PowerShell), from the repo root:**
```powershell
Copy-Item .env.example .env
notepad .env
```
> ⚠️ **Windows: Notepad may save it as `.env.txt`**, which the backend won't find. In File Explorer turn on
> **View → Show → File name extensions** (Windows 11) or **View → File name extensions** (Windows 10), then rename
> `.env.txt` to `.env`. In Notepad's "Save as" dialog, choose **Save as type: All files** and type the name `.env`.
> Check in PowerShell: `Get-ChildItem -Force .env*` should list `.env` and `.env.example` only.

Then fill in:

| Variable | Where to get it |
|---|---|
| `GEMINI_API_KEY` | aistudio.google.com → Get API key |
| `TELEGRAM_BOT_TOKEN` | Telegram → @BotFather → `/newbot` |
| `GOOGLE_CALENDAR_ID` | Google Calendar → calendar settings → Calendar ID |
| `GOOGLE_SERVICE_ACCOUNT_FILE` | Google Cloud → Service Account → JSON key (keep at `backend/service-account.json`) |
| `ESCALATION_MINUTES` | Minutes before escalating to HOD (use `2` for demos) |
| `TARS_DEMO_PASSWORD` | Choose one: the login password for **every** seeded user. Applied by `seed.py` and the demo reset. Share it with your team privately, never in the repo. |
| `TARS_SESSION_SECRET` | Long random string that signs login tokens: `python3 -c "import secrets; print(secrets.token_urlsafe(48))"` (Windows: `py -c ...`). If empty, everyone is logged out whenever the backend restarts. |
| `TARS_PASSWORDLESS_LOGIN` | Leave empty. `1` allows login without a password (local testing only). |
| `TARS_DEMO_MODE` | `1` enables the HOD's "Reset demo" (see below). Leave empty otherwise. |

After changing `TARS_DEMO_PASSWORD`, run `python3 app/seed.py` (or the demo reset) so the new password is applied.
Login is `login id + password` (USN for students, staff ID like `F08`/`H01` for staff).

> ⚠️ `.env` and `service-account*.json` are gitignored. Never commit keys.

**Google Calendar setup:** in Google Cloud create a service account, download its JSON key to
`backend/service-account.json` (gitignored; the path in `.env` is resolved from the repo root), and share the department
calendar with the service account's email with **"Make changes to events"**. Put the calendar's ID (Calendar settings →
Integrate calendar → Calendar ID) in `GOOGLE_CALENDAR_ID`. TARS then adds an event for every substitution/move and the demo
reset removes them. If either value is missing, the backend logs "Google Calendar disabled" and carries on.

**Telegram setup (2 min):** create the bot with @BotFather and put its token (looks like `123456789:AA…`, ~45 chars) in
`TELEGRAM_BOT_TOKEN`, then start the backend (it polls; no webhook). On each phone, open the bot, send `/start`, reply
with your login id (`F08`, `H01`, or a USN), then with the password (the bot deletes that message). Link the substitute (F08, and F07 for the DS Lab) and the HOD (H01) **after**
the final `python3 app/seed.py`, because reseeding clears the links. Without a token the backend runs normally and logs
that Telegram is disabled.

## Repeatable demo (reset between runs)
1. In `.env` set `TARS_DEMO_MODE=1`, then start the backend. Leave it unset outside demos: the reset endpoint then returns 404.
2. Once: `python3 app/seed.py` (fresh DB, applies `TARS_DEMO_PASSWORD`), then link the phones on Telegram
   (`/start` → `F08` → password; same for `F07` and `H01`).
3. Run the scenario below.
4. Reset, either with the HOD's **Reset demo** button (shown when `GET /api/meta` returns `demo_mode: true`), or:
   ```bash
   TOKEN=$(curl -s -X POST http://localhost:8000/api/auth/login -H "Content-Type: application/json" \
     -d '{"login_id":"H01","password":"<your TARS_DEMO_PASSWORD>"}' | python3 -c "import json,sys;print(json.load(sys.stdin)['token'])")
   curl -X POST http://localhost:8000/api/admin/reset-demo -H "Authorization: Bearer $TOKEN"
   # {"status":"reset","slots":72}
   ```
   This restores the seeded timetable and names, clears incidents, decisions, nudges, RSVPs and pending Telegram
   confirmations, and cancels escalation timers. Telegram links are kept, so there's no relinking. Every open browser
   gets a `demo_reset` event and refreshes. Old Accept/Decline buttons from earlier runs stop working.
5. Repeat from step 3. Only re-run `seed.py` if you edited `seed_data.json`'s structure: it rebuilds the DB and clears Telegram links.

The reset only touches `backend/tars.db`. It never writes `.env`; the only setting it uses is `TARS_DEMO_PASSWORD`
(already loaded at startup) to re-apply passwords. If that is empty, existing passwords are kept, so nobody is locked out.

## Demo scenario
The seed data includes a ready-made scenario:

1. Switch role to **Faculty**, then report **F01** absent on **Monday**.
2. This affects **CSE-A**: DS Lab (P1) and Data Structures (P2).
3. CSE-A's Data Structures attendance is **71%** (below 75%), so TARS refuses to cancel.
4. TARS picks **F08**: they teach DS, are free at that time, and have the lowest load.
5. The validator confirms there's no clash → the change is saved → the Calendar event is created → the substitute gets a Telegram ping.
6. No reply within 2 minutes → the HOD is alerted on Telegram.
7. Switch to **Student**: the grid shows the class as *TARS Re-planned*, with a nudge. Switch to **HOD**: the audit log shows TARS's full reasoning.
